## 프로젝트 개요

대규모 언어 모델(LLM)이 긴 문서를 처리할 때 발생하는 토큰 사용량 문제를 줄이기 위해, 질문과 관련된 핵심 정보를 선별하는 방법을 연구했습니다.

단순히 입력 문맥을 줄이는 것이 아니라, 질문에 필요한 정보를 최대한 유지하면서 답변 정확도와 토큰 효율성을 함께 고려하는 것을 목표로 했습니다.

## 진행 내용

### 1. 실험 환경 구성

Ubuntu 환경에서 Ollama를 활용하여 LLM을 실행하고, Python으로 실험을 수행할 수 있는 환경을 구성했습니다.

### 2. 문맥 처리 방법 비교

질문에 필요한 정보를 효율적으로 제공하기 위해 다음 방식들을 비교했습니다.

- **Truncate:** 입력 문맥을 앞부분부터 일정 길이까지 유지하는 방식
- **BM25:** 질문에 포함된 단어와 문장 사이의 관련성을 계산하여 문맥을 선택하는 검색 방식
- **Compress:** 소형 언어 모델을 활용하여 질문에 필요한 정보를 선별하고 압축하는 방식
- **Hybrid:** BM25로 선택한 문장을 우선 활용하고, 필요한 경우 압축 결과를 보완적으로 사용하는 방식

각 방식은 문맥을 줄이는 원리와 정보 보존 특성이 다르므로, 입력 토큰 수뿐 아니라 실제 답변 정확도도 함께 비교했습니다.

### 3. 성능 평가 및 결과 분석

LongBench와 HotpotQA 데이터셋을 활용하여 각 방식의 답변 정확도와 입력 토큰 사용량을 비교했습니다.

특히 답변 정확도뿐 아니라 질문에 필요한 근거 정보가 얼마나 유지되는지도 함께 살펴보았습니다.

이를 통해 문맥 압축이 토큰 사용량을 줄이는 데 얼마나 효과적인지, 그리고 답변 품질에는 어떤 영향을 미치는지 분석했습니다.

## 실험 결과

### 1. 초기 LongBench 실험 비교

초기 실험에서는 Truncate, BM25, Compress 방식의 답변 정확도(F1)와 평균 입력 토큰 수를 비교했습니다.

| 문맥 처리 방식 | F1 점수 | 평균 입력 토큰 수 |
|---|---:|---:|
| Truncate | 0.349 | 2,402 |
| BM25 | **0.384** | 1,909 |
| Compress | 0.306 | **98** |

위 표는 초기 실험 결과이며, 이후 수정된 실험이나 다른 데이터셋에서의 결과를 대표하지 않습니다.

초기 실험에서 BM25는 세 방식 중 가장 높은 F1 점수를 기록했습니다. 반면 Compress는 평균 입력 토큰 수가 가장 적었지만 답변 정확도는 상대적으로 낮았습니다.

이는 입력 문맥을 크게 줄이는 것과 필요한 근거 정보를 보존하는 것이 서로 다른 문제임을 보여주었습니다.

### 2. 압축 방식 개선

초기 실험 이후 문맥 압축 과정에서 원문 정보가 제대로 유지되지 않는 사례를 검토했습니다.

특히 출력 문장을 원문과 비교하는 처리 과정의 문제를 개선하기 위해 문장 식별자(sentence ID)를 활용하는 방식으로 수정했습니다.

수정 후 실험에서 Compress의 F1 점수는 **0.324**, 평균 입력 토큰 수는 **118토큰**으로 나타났습니다.

초기 실험보다 답변 정확도가 개선됐지만, 이것만으로 다른 방식보다 우수하다고 결론 내릴 수는 없었습니다.

### 3. 근거 정보 보존의 중요성

실험을 분석하면서 입력 문맥에 정답을 찾는 데 필요한 근거 정보가 포함되어 있는지가 중요하다는 점을 확인했습니다.

근거 정보가 충분히 보존된 사례에서는 압축 방식의 답변 정확도가 다른 방식과 가까워지는 경향이 나타났습니다.

따라서 압축된 문맥의 길이만 측정하는 것이 아니라, **질문에 필요한 정보가 얼마나 남아 있는지** 함께 확인해야 한다는 결론을 얻었습니다.

### 4. Hybrid 방식 검토

BM25와 Compress의 장점을 함께 활용하기 위해 Hybrid 방식도 검토했습니다.

BM25가 질문과 직접 관련된 문장을 찾아주는 장점이 있는 반면, 단순 단어 일치만으로는 필요한 정보를 모두 확보하지 못할 수 있습니다.

이를 보완하기 위해 BM25로 선택한 문장을 중심으로 문맥을 구성하고, 필요한 경우 압축 결과를 보완적으로 사용하는 접근을 살펴보았습니다.

일부 질문에서는 이러한 방식이 도움이 되었지만, 모든 질문에서 일관된 성능 향상을 확인한 것은 아닙니다.

### 5. 결과 분석 및 한계

실험 결과를 통해 다음과 같은 점을 확인했습니다.

- Compress는 입력 토큰 수를 크게 줄일 수 있지만, 필요한 정보가 누락되면 답변 정확도가 낮아질 수 있습니다.
- BM25는 질문과 단어가 일치하는 정보를 찾는 데 유용하지만, 질문의 의미를 깊이 이해하는 방식은 아닙니다.
- Truncate는 단순하고 빠르지만, 문서 뒤쪽에 중요한 정보가 있을 때 이를 놓칠 수 있습니다.
- Hybrid 방식은 각 방법의 단점을 보완할 가능성이 있지만, 실제 효과는 질문과 문맥의 특성에 따라 달라집니다.

따라서 연구의 핵심 과제는 단순한 토큰 감소가 아니라 **제한된 입력 길이 안에서 질문에 필요한 근거 정보를 최대한 보존하는 것**이라고 판단했습니다.

## 배운 점

이번 연구를 통해 LLM의 성능을 평가할 때 답변 정확도뿐만 아니라 토큰 사용량과 정보 보존 정도도 함께 고려해야 한다는 점을 배웠습니다.

또한 실험 환경을 구성하고 여러 방법의 결과를 비교하면서 데이터 처리, 성능 평가 및 결과 분석에 대한 경험을 쌓을 수 있었습니다.

특히 예상한 결과와 실제 측정 결과가 다를 수 있다는 점을 경험하면서, 객관적인 실험 결과를 바탕으로 방법의 장점과 한계를 판단하는 것이 중요하다는 사실을 알게 되었습니다.

또한 다양한 질문 유형과 데이터셋에서 실험을 진행하여 문맥 압축의 효과가 달라지는 원인을 분석할 계획입니다.

궁극적으로는 답변 정확도를 최대한 유지하면서 입력 토큰 사용량을 줄일 수 있는 효율적인 문맥 처리 방법을 연구하는 것이 목표입니다.
